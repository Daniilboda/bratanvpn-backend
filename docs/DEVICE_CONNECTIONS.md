# Device connections — мультиустройство и лимит активных VPN

Статус: **целевая схема зафиксирована в** `.cursor/rules/bratanvpn.mdc` (2026-07-29).  
В **коде** пока ещё может работать legacy MVP «1 access key = 1 устройство» — внедрение по Excel `#46+`.

Связанный трекер: `docs/BratanVPN_status.xlsx` (задачи с `#46` и далее).

---

## 1. Зачем меняем модель

Проблемы текущей схемы (1 ключ = 1 `device_id`):

- переустановка приложения → новый локальный `device_id` → «ключ уже на другом устройстве»;
- смена телефона / ноутбука требует revoke/restore или новый ключ;
- пользователь не видит и не управляет привязанными устройствами.

Новая модель решает это через **привязку многих устройств** к одному access key и **лимит одновременных VPN-сессий**.

---

## 2. Концепт (как должен работать продукт)

### Выдача доступа

1. Пользователь получает **один** access key (лично / через Telegram-бота).
2. Скачивает приложение (Windows / Android).
3. Вводит access key → происходит **привязка устройства** (bind).
4. VPN **сразу не включается**.
5. На главном экране появляется обычная кнопка «Подключиться» — дальше VPN стартует **без повторного ввода ключа**.

### Несколько устройств

- Тем же access key можно привязать **любое количество** устройств (телефон, второй телефон, ноутбук, …).
- Одновременно в состоянии «VPN подключён» могут быть **не больше 3** устройств.
- Привязка ≠ активное подключение:
  - привязанных устройств может быть 5, 10, …;
  - активных VPN-сессий — максимум 3.

### Сценарий «уже 3 в сети»

1. Устройства A, B, C подключены к VPN (3/3).
2. Пользователь привязывает устройство D (ключ вводится один раз на D).
3. На D нажимает «Подключиться» → **отказ**: лимит 3 активных подключений (понятное сообщение).
4. Отключает VPN на A → на D подключается **без ввода ключа** (D уже привязан) → снова 3/3 (B, C, D).
5. Снова «Подключиться» на A → отказ (лимит).
6. Отключает VPN на B → на A снова подключается одной кнопкой.

### Потеря телефона / удаление приложения

- После переустановки пользователь снова вводит **тот же** access key → устройство привязывается заново (новый локальный `device_id` / запись Device).
- Старая «мёртвая» привязка может остаться в списке — пользователь отвязывает её в настройках (или «отвязать все»).
- Активный слот на потерянном устройстве можно **удалённо разорвать** из настроек с другого устройства.

---

## 3. Управление устройствами (настройки)

В экране настроек пользователь видит **список привязанных устройств**, например:

| Устройство        | Статус              | Действия                          |
|-------------------|---------------------|-----------------------------------|
| Huawei Notebook   | VPN подключён       | Отключить VPN / Отвязать          |
| Pixel 7           | Привязан, не в VPN  | Отвязать                          |
| Старый телефон    | Не в сети давно     | Отвязать                          |

Возможности:

1. **Отвязать одно устройство** — удалить bind; на том устройстве потребуется снова ввести ключ (если ещё есть доступ к приложению).
2. **Отвязать все устройства** — сброс всех bind’ов по этому ключу.
3. **Удалённо разорвать VPN** на другом устройстве — освободить один из 3 слотов, не обязательно отвязывая устройство.

Идентификация в UI: имя устройства (модель / то, что сообщил клиент) + платформа + дата последней активности.

## 4. Существенные изменения относительно текущего MVP

| Было (MVP сейчас) | Станет (этот план) |
|-------------------|--------------------|
| 1 ключ = 1 `device_id` на `AccessKey` | 1 ключ = много устройств (таблица Device / аналог) |
| Повторная активация с другим `device_id` запрещена | Привязка новых устройств тем же ключом разрешена |

## 5. Предлагаемая модель данных (черновик)

### AccessKey (ключ подписки / доступа)

- `id`, `key`, `status` (`created` / `activated` / `revoked` — уточнить семантику `activated`: «есть хотя бы одно устройство» vs оставить как сейчас)
- лимит: `max_active_sessions = 3` (константа или поле)
- **без** единственного `device_id` / `vpn_public_key` / `vpn_ip` на ключе (переезд на Device)

### Device (привязка)

- `id`
- `access_key_id`
- `device_id` (клиентский стабильный id в vault приложения)
- `display_name` / `platform` (`windows` / `android`)
- `vpn_public_key` — сохраняется при **bind** (нужен для add peer при connect)
- `vpn_ip` — **nullable**; заполняется только пока устройство в активной VPN-сессии (см. §5.1)
- `created_at`, `last_seen_at`
- флаги/состояние сессии: `vpn_connected` **или** отдельная таблица сессий (предпочтительнее сессия, чтобы remote disconnect был явным)

### VpnSession (опционально, но удобно для лимита 3)

- `device_id` / `device_fk`
- `started_at`, `ended_at`
- `active` bool  
- при желании дублировать/ссылаться на выданный `vpn_ip` сессии  
Счётчик активных по `access_key_id` ≤ 3.

Точные имена полей и миграции — на этапе реализации.

### 5.1. Политика `vpn_ip` (зафиксировано 2026-07-29)

**Смысл:** `vpn_ip` — внутренний адрес клиента в сети AmneziaWG (например `10.8.0.x`), поле `Address` в conf. Нужен peer’у на VPS, пока туннель/сессия активны.

**Решение:** `vpn_ip` относится к **подключённым** (активная сессия), не ко всем привязанным.

| Момент | `vpn_public_key` | `vpn_ip` | Peer на VPS |
|--------|------------------|----------|-------------|
| Bind (привязка) | сохранить на Device | `NULL` | не добавлять |
| Connect (слот свободен) | уже есть | выдать из пула → записать | `add` peer |
| Disconnect / remote disconnect | оставить на Device | очистить (`NULL`) | `remove` peer |
| Устройство только привязано, VPN off | есть | `NULL` | нет |

**Почему не выдавать IP на bind**

- лимит «max 3 активных» должен совпадать с числом peer’ов на сервере;
- привязанных устройств может быть больше трёх — им не нужны постоянные IP;
- иначе отключённое устройство могло бы оставаться peer’ом и обходить смысл слотов.

**Повторный connect** того же Device: можно выдать новый `vpn_ip` (проще для MVP) или стараться вернуть прежний (`last_vpn_ip` — опционально позже). Обязательного sticky IP нет.

**Итог:** колонка `vpn_ip` живёт на Device (или на VpnSession), но **заполнена только у активных**; у просто привязанных — всегда `NULL`.

## 6. API (черновик контрактов)

Имена предварительные; финальные пути согласовать при кодировании.

| Действие | Идея |
|----------|------|
| Привязка устройства | `POST /api/v1/devices/bind` (access key + device_id + vpn_public_key + display_name) → конфиг/секреты устройства; **без** старта туннеля |
| Список устройств | `GET /api/v1/devices` (по access key + device_id вызывающего) |
| Отвязать одно | `DELETE /api/v1/devices/{id}` или `POST .../unbind` |
| Отвязать все | `POST /api/v1/devices/unbind-all` |
| Старт VPN | Занять слот (если активных меньше 3) → выдать `vpn_ip` → add peer → клиент поднимает туннель |
| Стоп VPN (локальный) | клиент stop + освободить слот → `vpn_ip = NULL` → remove peer |
| Remote disconnect | то же с сервера; клиент-жертва гасит туннель на validate/poll |
| Validate / heartbeat | периодически: ключ не revoked + устройство ещё привязано + при необходимости sync remote-disconnect |

Клиент:

- после успешного bind ключ и `device_id` в vault;
- кнопка «Подключиться» **не** спрашивает ключ, если bind есть;
- при лимите 3 — диалог с понятным текстом (и ссылкой/ходом в настройки устройств).

## 7. Клиентский UX (кратко)

1. Первый запуск / нет bind → диалог access key → bind → главный экран (disconnected).
2. Есть bind → одна кнопка, как сейчас.
3. Настройки (шестерёнка) → «Устройства» → список + действия.
4. Remote disconnect другого устройства → у того клиента на следующем validate/poll туннель гасится.

Интервал validate/poll: как сейчас (старт, перед connect, периодически, resume); для remote disconnect желательно не реже текущего poll или отдельный короткий poll **пока** VPN активен.

## 10. Критерии готовности этой фичи

- Один ключ привязывает ≥4 устройств.
- Одновременно VPN поднимается максимум на 3.
- 4-е получает отказ с понятным UI.
- После disconnect одного из трёх 4-е (уже привязанное) подключается без ввода ключа.
- Из настроек: отвязать одно / все; remote disconnect чужого активного VPN.
- Revoke ключа админом по-прежнему гасит доступ на всех устройствах.
- Приватный VPN-ключ по-прежнему не покидает устройство.
