# Отчёт о тестировании backend (pytest)

Дата прогона: **2026-07-23**  
Результат: **все 20 проверок прошли успешно** (около 1 секунды)  
Окружение: Windows, Python 3.13, виртуальное окружение `backend/.venv`

---

## 1. Зачем эти тесты

Нужно автоматически проверить главный сценарий приложения, без ручных кликов и без подключения к настоящему VPS по SSH:

1. админ создаёт ключ доступа;
2. клиент активирует устройство этим ключом;
3. сервер отдаёт VPN-конфигурацию;
4. проверка доступа (`validate`) говорит, что всё в порядке;
5. админ отзывает ключ;
6. после отзыва доступ закрыт: конфиг не выдаётся, активировать снова нельзя.

Дополнительно проверяем «необычные» ситуации: другое устройство, сбой VPN-агента на сервере, вход в админку с неверным паролем/ключом, правильный формат ключа и раздачу IP-адресов.

## 2. Как устроены проверки

### 2.1. Запросы к API без запуска сервера вручную

Тесты обращаются к FastAPI через библиотеку **httpx** и режим **ASGITransport** (запросы идут прямо в код приложения, как HTTP, но отдельный веб-сервер вроде `uvicorn` не запускается).

Приложение работает **в том же процессе**, что и сами тесты.  
Адрес в тестах: `http://test` — это просто условный адрес, не настоящий сайт в интернете.

### 2.2. База данных

Вместо боевого PostgreSQL тесты используют **SQLite в памяти** (`sqlite+aiosqlite:///:memory:` — лёгкая база, которая существует только пока идут тесты и потом пропадает):

* таблицы создаются из моделей SQLAlchemy (описание таблиц в коде);
* каждый тест стартует с **пустой свежей базы** (через заготовку pytest — **fixture** `db_engine`: кусок кода, который готовит окружение перед тестом);
* обычная функция приложения «дай подключение к БД» (`get_db`) в тестах подменяется на подключение к этой тестовой SQLite;
* **твоя настоящая PostgreSQL не меняется и не читается**.

Зачем так: быстро, тесты не мешают друг другу и не портят реальные данные, Docker для каждого прогона не нужен. Для нашей таблицы ключей доступа этого хватает.

### 2.3. VPN-агент (AmneziaWG)

Настоящие команды «добавить устройство на VPN» / «удалить устройство» по SSH **не вызываются**. Вместо них стоят **моки** (заглушки: притворяются, что агент ответил «ок», без реального сервера). Делается через `AsyncMock` и `patch` из стандартной библиотеки Python.

Подменяются функции:

* `add_peer_async` — «добавить peer» (устройство/ключ на VPN-сервере);
* `remove_peer_async` — «убрать peer».

Так мы проверяем правила API и запись в базу, не трогая VPS и пароли SSH.

В проверках «что если сломалось» заглушка специально выдаёт ошибку `VpnAgentError`. Тогда API должен ответить **502** (сервер не смог выполнить действие из‑за сбоя агента), а статус ключа в базе не должен «застрять» в неправильном состоянии.

### 2.4. Админский API

Для админских запросов передаётся заголовок `X-Admin-Key` — тот же секрет, что в настройках (`admin_api_key` из `.env`).

Отдельно проверяем:

* **401** — ключ админа неверный (вход запрещён);
* **422** — запрос кривой (например, заголовок с ключом вообще не передали).

### 2.5. Проверки health (состояние системы)

Файл `tests/test_health.py` отдельный: вместо настоящей БД подставляется простая фальшивая сессия, ответы агента/диска/Telegram тоже заглушки. Эти тесты не используют свежую SQLite из основного сценария.

## 3. Что именно проверялось

### 3.1. Главный сценарий — `test_critical_access_flow.py`

| Шаг | Запрос | Ожидание |
|-----|--------|----------|
| Создать ключ | `POST /api/v1/admin/keys` | успех (`200`), статус `created`, ключ вида `BRATAN-…` |
| Проверка до активации | `POST /api/v1/validate` | `ready_to_activate` (ключ есть, ещё не привязан к устройству) |
| Конфиг до активации | `GET /api/v1/vpn/config` | отказ `403` — ключ ещё не активирован |
| Активация | `POST /api/v1/activate` | успех, выдан `vpn_ip` из сети `10.8.0.x` (не адрес шлюза `.1`), вызвали «добавить peer» |
| Повторная активация того же устройства | снова activate | успех, тот же IP |
| Проверка доступа | validate | `valid` (можно пользоваться) |
| Конфиг | vpn/config | успех, версия схемы `1`, протокол `amneziawg`, **приватного ключа в ответе нет** |
| Отзыв | `PATCH /api/v1/admin/keys/revoke` | статус `revoked`, вызвали «убрать peer» |
| После отзыва | validate / config / activate | отозван / отказ `403` |

Дополнительно: **восстановить ключ → активировать снова** (после отзыва ключ возвращается в «создан», можно заново активировать с новым публичным VPN-ключом, конфиг снова выдаётся).

### 3.2. Необычные ситуации — `test_activation_edges.py`

* несуществующий ключ → activate `404` (не найдено), validate `not_found`, config `404`;
* **другое устройство** (тот же ключ, другой `device_id`) → отказ `403`, validate `device_mismatch`;
* **агент упал при активации** → `502`, ключ остаётся «готов к активации», повторная попытка проходит;
* **агент упал при отзыве** → `502`, доступ всё ещё `valid` (отзыв в базу **не сохранился**).

### 3.3. Админка — `test_admin_keys.py`

* без заголовка админа → `422`;
* неверный админ-ключ → `401`;
* список ключей, фильтр по статусу `created`, получение одного ключа, ответ «не найден»;
* отозвать несуществующий / уже отозванный ключ;
* восстановить ключ, который не был отозван → ответ `not_revoked`.

### 3.4. Проверки отдельных функций — `test_access_key_unit.py`

Здесь тестируются маленькие функции сами по себе, без всего HTTP API:

* формат ключа `BRATAN-` + 16 шестнадцатеричных символов;
* ключи при генерации не повторяются;
* раздача IP пропускает адрес шлюза `10.8.0.1` и уже занятые адреса.

### 3.5. Health — `test_health.py` (раньше)

* всё в порядке;
* система **частично неисправна** (`degraded`), если VPN-агент не отвечает;
* в Telegram уходит предупреждение, но не чаще, чем раз в заданный интервал (**cooldown** — пауза против спама); когда всё восстановилось — отдельное сообщение «снова ок».

## 6. Чего эти тесты пока не покрывают

* Настоящий PostgreSQL и миграции Alembic (скрипты изменения структуры БД) в этом прогоне не гоняются; таблицы создаются сразу из моделей на SQLite.
* Настоящий AmneziaWG-агент и реальный VPN-туннель не поднимаются.
* Нет тестов на большую нагрузку и на ограничение частоты запросов (rate limit).
* Тесты Flutter-клиента лежат отдельно (`apps/client/test/`) и в этот отчёт не входят.

Позже полезно добавить: прогон на Postgres (по желанию, отдельной меткой), плюс проверку, что JSON ответа `vpn/config` совпадает с тем, что ждёт Flutter-клиент.

Главный путь **активация → конфиг → проверка доступа → отзыв** закрыт автотестами: база тестовая (не боевая), VPN-агент заменён заглушкой. Все **20** проверок зелёные. Для локальной разработки этого достаточно, чтобы вовремя заметить, если сломается доступ или админка, ещё до выкладки на VPS.
